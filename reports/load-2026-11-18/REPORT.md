## Условия и ограничения

- Внешний GitHub runner → публичный HTTPS → `GET /api/catalog?limit=30` с действующим токеном временного тестового участника.
- Сервер сообщает 2 CPU; ранее проверено около 4 ГБ RAM. В этом прогоне загрузка CPU, память, дисковые задержки и запросы БД по отдельности не профилировались, поэтому точная причина предела не установлена.
- Модель закрытая: каждый из N исполнителей отправляет следующий запрос после ответа на предыдущий. Измерена фактическая скорость завершения, а не заданная независимая интенсивность поступления.
- Ступени 1, 10, 25, 50, 100, 250, 500, 1000; новые запросы отправлялись 15 секунд на каждой ступени, затем ожидалось завершение. Между ступенями пауза 3 секунды.
- Предусмотрены остановки при доле ошибок >1%, двух подряд неуспешных проверках здоровья или p95 >3 секунд. Ступени 2500 и 5000 не запускались, поскольку на 1000 сработал порог p95.
- Временный участник и его сессии удалены после теста. Рабочие участники, партнёры, скидки и посещения не изменялись.
- Один тестовый аккаунт не моделирует тысячи различных участников. Не измерены массовый вход с хешированием паролей, QR-транзакции, загрузка изображений, пуши и смешанный пользовательский сценарий.
- Короткие ступени не доказывают круглосуточную устойчивость. Этот прогон не определяет абсолютный предел сервера и не отделяет возможные ограничения генератора и сети от сервера.

## Практический вывод

В этом сценарии скорость перестаёт заметно расти после примерно 200 запросов/с, а очередь увеличивает задержки. Для старта разумно ориентироваться на проверенную ступень до 100 одновременно выполняемых запросов с p95 менее секунды, оставляя запас; это не гарантия для других операций или длительной эксплуатации.

Для увеличения пропускной способности нужны профилирование API и PostgreSQL, проверка индексов и повторяющихся запросов, кэширование каталога с корректной инвалидацией и разграничением организаций, отдельная раздача изображений, затем масштабирование экземпляров API и БД по измерениям. Проверять цель в миллионы запросов/с следует на отдельном согласованном стенде распределёнными генераторами. На текущем рабочем VPS рост нагрузки остановлен без потери доступности.

## Повторение

GitHub → Actions → **Measure authorized staged read-only server capacity** → Run workflow → main. Результаты: артефакт `qazaqmetal-load-verification`, файлы `results.json` и `progress.json`. Нужен действующий `DEPLOY_SSH_PASSWORD` в repository Secrets. Workflow использует проверку отпечатка сервера перед SSH-аутентификацией и создаёт собственную временную учётную запись. Не запускать параллельно с обновлением сервера или другим нагрузочным тестом.

Скрипт: `.github/scripts/load_readonly.py`; workflow: `.github/workflows/qazaqmetal-load.yml`. Паролей и токенов в протоколе нет.
